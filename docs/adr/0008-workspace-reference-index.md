# 工作区引用索引与根内相对路径解析

## 状态

2026-09-28 用户结束访谈并授权开票；架构原则已接受，尚未实施。存储引擎经前置测量票（#195，2026-09-28 完成）选定「紧凑分片快照 + 内存关系表」，见下节。

## 决定

- 多根工作区分别索引，各根为独立资源边界。链接仅按来源文档相对路径解析，不跨根，不作 basename、目录距离或字典序候选搜索。同目录省略扩展名双链默认指向 Markdown。
- 索引是可重建的派生缓存，保存文件元数据、mtime 和引用关系，不复制全文或附件内容。其他类型文件仅作引用目标登记。
- 缓存按工作区私有存储、根级分区，Remote SSH 存宿主侧；允许不同工作区重复缓存，同工作区多窗口须协调写入。
- 引用自动更新覆盖 VSCode 内文件/目录更名和移动，依据明确旧目标计算新相对路径，不能覆盖并发输入或生成跨根引用。失败明确 Alert，不后台迟到改写。
- 图片缓存刷新作为本批功能，事件驱动加周期核验；图源明确删除后撤下旧图并显示找不到，断连与权限失败单独处理。
- 插件自有设置页提供排除规则、恢复默认、清理缓存与完整重建。健康缓存不按固定时间作废，不建跨工作区闲置清理服务。

## 旧决策与访谈修订

替代 ADR-0002 中不建持久索引、按文件名搜索与同名用户选择的限制，旧 ADR 保留历史。访谈中曾提出的跨根补查、最近优先、字典序择一和同名冲突放弃/覆盖 Alert 均已被最终相对路径决定撤销，不得重新实现。

## 存储选型（#195 前置测量补充，2026-09-28）

### 决定：紧凑分片快照 + 内存关系表

引用索引的持久化采用**列式紧凑分片快照**（`src/shared/vaultIndexSnapshot.ts`），启动加载后在内存重建文件表、边表与反链索引；**不引入 SQLite**。测量依据与全部原始数字见 [基准数据](../perf/data/vault-index-storage-bench.json) 与 [解读文档](../perf/2026-09-vault-index-storage.md)，本节只落决定与策略。

淘汰 SQLite（sql.js WASM 接入形态）的理由：

- **宿主约束**：Node 18 API 面无内置 SQLite（Node 22 才加入），仓库锁定 VSCode 1.86 且打包自包含，不能要求用户安装 native sqlite3；唯一可兼容旧宿主形态是 sql.js 这类 WASM 翻译版。
- **同步阻塞**：sql.js 在 JS 线程同步执行 SQL，首建/大事务期间事件循环被完全阻塞——10 万篇档实测最长 **8.09 秒不让出事件循环**（建库 4.0 s + 全库导出约 4 s，且每次持久化均整库导出）。在扩展宿主进程内即全部扩展逻辑无响应 8 秒，与「后台任务不拖慢编辑」的 Remote SSH 目标直接冲突；该阻塞发生在库引擎内部，JS 层无法切片。
- **冷恢复与查询**：反链查询是面板高频路径，内存关系表为 O(1) 命中，SQL 查询每次跨 JS/WASM 边界（慢一个数量级以上）；冷恢复需整库反序列化，明显慢于快照分片加载。
- **包体**：sql.js 胶水与 WASM 产物会显著膨胀 VSIX，违反打包体积红线（`scripts/release.mjs` 的 SIZE_LIMITS）。

SQLite 胜出的场景（单文件/批量的纯事务更新耗时）不构成翻案理由：生产调度本就把落盘合并为低频批量写（#194 生命周期初值：连续输入约 2s 合并一次、磁盘合并写），快照方案在该节奏下的提交成本可接受；其代价（更新时重写受影响片）由分片粒度控制（见「容量与回收阈值」）。

### 快照格式与崩溃提交/恢复策略

目录布局（`baseDir = <context.storageUri>/vsidian-index/<rootKeyOf(root.uri)>`，按根分区；Remote SSH 时 storageUri 落宿主侧，不写笔记目录）：

- 每代一个 `gen-<6位代号>-<写者标签>` 目录：`manifest.json`（格式版本、片清单、每片校验和）+ `shard-NNN.json`（列式紧凑 JSON：字符串表 + 文件行 + 边行）。
- `CURRENT` 纯文本文件指向当前代目录名，是**唯一提交点**。

崩溃安全三要素（实现于 `vaultIndexSnapshot.ts`，契约测试钉住）：

1. 片与 manifest 均以「写临时文件 + rename」原子落盘；manifest 携带每片 FNV-1a 校验和，半截写入可检出。
2. `CURRENT` 最后写：写它之前新代目录已完整；读者要么看到旧代、要么看到完整新代，永不读到半新半旧。
3. 恢复按「CURRENT 指向代 → 代号降序扫描」回退；全部不可用返回 null，上层走全量重建（索引是可重建缓存，损毁不丢事实源）。

格式版本（`SNAPSHOT_FORMAT_VERSION`）随结构不兼容演进递增，旧版本代拒读并回退。

### 同工作区多窗口写入协调

同一工作区在多个 VSCode 窗口打开时存在多个扩展宿主进程，共享同一存储目录。协调不依赖跨进程锁，靠三个不变量：

- **写者标签**：代目录名含随机写者段，两窗口同代号提交不会互相覆盖文件。
- **CURRENT 原子替换**：提交以 rename CURRENT 为准，最后提交者胜出；任一时刻读者都能读到某个完整代。
- **回收保守性**：只回收「代号不高于当前 CURRENT 指向代且非其继承源」的目录与 `tmp-` 残留；并发窗口的完整旧代最多晚一轮被回收。

竞争代价：两窗口基于同一旧代各自提交时，后写者的 CURRENT 覆盖前者，前者本轮索引更新不进快照。这是可接受的缓存语义——索引仅为派生缓存，周期核验（mtime+size 清单比对）会检出漂移并增量重建，事实源（Markdown 正文）不受影响。

### 资源版本结构

- 文件条目：`mtimeMs` + `size` + `contentVersion`（每次重新解析递增）。mtime+size 仅作变化筛选，不是内容一致性证明；完整重建是兜底恢复路径。
- 出链边：保留原始目标文本与按来源目录解析的根内相对规范路径（断链、越界、https 为 null），以及正文内 LF 偏移区间（引用更新定位用）。
- 图片资源版本（#201 消费）：目标 URI + mtime + size + 已观测变化代次；收到变更事件即使元数据相同仍失效（防 mtime 粒度漏检）。
- 未保存内容为窗口内存覆盖层，不写入已保存快照；旧扫描结果不得覆盖新版本（contentVersion 单调递增仲裁）。

### 容量与回收阈值

- **分片粒度**：片数初值按库容自适应——约 16 片（≤1 万篇）、64 片（1–10 万篇）、256 片（>10 万篇），单片目标 ≤1500 文件；写入量与片数的实测权衡见解读文档「分片敏感性」节（片数加大写盘字节近似线性下降、耗时基本持平），#198 增量维护落地时按实测校准。
- **接线约束（事件循环）**：快照引擎的单次同步提交在 10 万篇档实测最长 3.72 s 不让出事件循环（整代序列化）。`planSnapshotCommit` 本票为纯同步函数；#197 接线时必须在片间交错让出（`setImmediate`/分批 await），把单次饿死切成百毫秒级切片——选型结论不变，此为实现层强制要求。
- **空间预算**：快照体积随边数线性增长（实测约每边 90–110 字节量级，含文件条目与 JSON 结构开销，数字见报告），健康态保留两代（当前代 + 继承源代）；继承片不重写，磁盘实际占用接近单代。
- **回收时机**：CURRENT 替换成功后回收旧代与 `tmp-` 残留；回收失败不阻塞提交（残留由下一轮回收清单兜底）。健康缓存不按固定天数失效。
- **降级路径**：全部代损坏 → 全量重建（进度与失败信息走设置页入口，#197/#198 接线）。

## 影响与验证

路径含义确定，旧有依赖跨目录短名搜索的链接将不再自动命中，须在交付说明中写明。不自动迁移旧正文。索引新增后台维护、并发及恢复成本，按 1千/1万/10万篇测量；Remote SSH 为重点验证场景。

以轻量分片快照为选型基线，与可兼容旧宿主的 SQLite 接入作实测比较；Node 18 API 面不能直接依赖 Node 22 内置 SQLite。选型票须记录提交恢复策略、预算和多窗口协调，之后方可实现持久化。（已由 #195 完成，见上节。）

详细契约、生命周期初值、验收与工单索引见 [实施规格](../specs/vault-index-backlinks.md)。
