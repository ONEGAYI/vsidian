# 引用文档视图分离读取、呈现与写回

## 状态

已接受架构方向，2026-09-29。用户确认先只读、后 Live，提前设计通用架构。尚未授权实施；产品范围与具体接口仍待细化。

## 背景

悬停预览和文档嵌入均展示另一个文档或其范围，未来需要可编辑视图。若底层只返回脱离文档身份的 HTML，后续无法可靠接入编辑；若读取强依赖完整编辑会话，又会使只读阶段背负不必要的实现成本。

## 决定

- 文档访问负责目标身份、带版本内容、范围定位、源位置映射、更新订阅与释放，不依赖写回能力。
- Reading 与 Live 是呈现模式，只读与可写是能力约束；悬停与嵌入是展示容器，容器不固定为某种模式。
- 首期实现 Reading 引用视图并禁用写入能力，不是只读 Live 视图；后续 Live 通过独立编辑端口写回目标文档，并与其他目标视图同步。
- 视图的滚动、选区和生命周期独立于文档内容；共享文档数据不等于共享同一个 DOM 或 EditorView。
- 通用接口保留文件类型扩展空间，Markdown 与附件可使用不同渲染器。已确认路线为一期 Reading 只读、1.5 期递归及表格与其他混排、二期 Live 编辑、三期 PDF 预览与嵌入；PDF 引擎与其他附件范围另行决定。
- 一期只在独占正文行挂载，但引用识别、文档访问和内部视图不依赖顶层块假设；为 1.5 期表格单元格与混排容器保留挂载适配层。

## 影响与取舍

可分期交付，同时避免只读 HTML 成为未来编辑的架构边界。首期仍需实现文档身份、版本与范围契约，并验证无写入端口的视图能正常刷新和释放。

此决定不要求首期实现 Live 写回或完整多视图编辑系统。后续必须具体设计版本冲突、局部范围重定位、撤销／保存归属及焦点与快捷键隔离，不能宣称接口预留已经解决这些问题。

详细建议、证据与访谈问题集中在 [共识草案](../specs/hover-preview-embed.md)。
