# Vsidian 附加组件的接入、运行与公开 API 治理

## 状态

已接受的设计方向，2026-10-04 起。用户确认术语、VSCode 安装入口、显式声明与注册识别、默认启用、独立 API 版本、文档治理、热切换、统一视图实例与普通 VSCode 扩展信任模型。用户设置统一管理、自定义设置页的范围与稳定 API 弃用期限也已确认。

加载选择「元数据声明 + 代码注册」，避免激活声明和代码双重定义行为而漂移。代码采用同一附加组件 VSIX 按需提供宿主与页面入口，调试复用 VSCode 工具。具体协议、装配实现与运行检查尚未实施。

2026-10-05 确认：附加组件菜单只允许新增，不允许覆写内置项；可捕获且可归因的异常发生后，暂停该组件在 Vsidian 中的全部注册功能，保留启用偏好并允许手动重试。

同日确认首批稳定 API 的六组能力范围，并以输入处理、内容渲染和界面操作三类样例共同验证。该确认确定能力范围，具体接口签名与数据模型仍待设计。

同日确认 Q21–Q23：附加组件设置及功能开关支持用户默认与工作区覆盖；设置值支持普通值、数组与对象；手动停用后仍可使用组件自己的设置页，故障暂停时由 Vsidian 提供配置与排障界面。设置侧栏分为「选项」「核心组件」「第三方组件」，后两个分组各设「已启用」「已停用」，按用户开关归类；故障暂停不改变分组，另外标注故障状态。

同日确认 Q24：核心组件也以独立 VSCode 扩展分发，共用公开 API。「核心组件」表示官方提供，与第三方组件按来源区分。

同日确认 Q25–Q26：Vsidian 先提供 API，再扫描附加组件声明、检查兼容性、唤醒合格扩展，由组件代码注册具体能力。首版要求组件宿主代码与 Vsidian 在同一扩展宿主中运行。

同日修订 Q27：同一操作的行为默认按既定顺序依次触发，用户可调序及逐项关闭，不把同一操作一概视为互斥。「行为冲突管理」入口位于组件管理设置页；注册行为时名称必填，简短说明和例子推荐提供。该修订取代将「先接管者生效」作为输入行为统一默认规则的前轮决定。

同日确认并补充 Q28：所有代码块语言均可由附加组件替代渲染，包括内置语言。新安装、兼容且已启用的渲染组件成功接入后自动替换当前显示，不要求用户再选择渲染器才生效；用户有需要时仍可主动调整。

同日修订并补充 Q29：每次文本修饰默认是可跟踪的原子操作，具有独立撤回边界；组件作者可明确声明某个操作非原子，与同一目标文档的上次原子操作一起撤回。非原子操作仍须跟踪，不自动将一次输入中的全部修饰合为一次撤销。

同日修订并确认 Q30：正常停用渲染器或组件时交回内置显示；整组件因故障被降级停用后，也允许内置接管。组件仍在运行但渲染代码有 bug 时，不自动接管，也不承诺识别或修复其错误输出。故障生命周期与显示接管须按实际组件状态区分。

## 背景

Vsidian 是 VSCode 扩展，也需要让第三方扩展自身能力。直接称「插件」无法区分安装平台与二次扩展的功能角色。已有内核菜单注册及覆写入口不代表已经具备通用附加组件框架，也不决定附加组件的公开权限。

Easy Typing 移植提供了输入类 API 的需求样本。用户要求先设计发现、加载和 API 边界，再制作验证组件，且 API 选型不能局限于这一案例。

## 决定

### 身份与 API 基础

- **术语**：正式称「Vsidian 附加组件」（Vsidian Add-on），代码侧统一使用 `addon`。使用「VSCode 扩展」描述安装平台概念；使用「Vsidian 附加组件」描述扩展 Vsidian 自身能力的组件。
- **官方与第三方**（Q24，2026-10-05）：核心组件是官方提供的附加组件，同样作为独立 VSCode 扩展经 VSCode 分发与安装，使用与第三方组件相同的公开 API，遵守同一套兼容与生命周期约定。「核心」用于区分来源，官方归属的具体识别方式尚待设计。
- **开发目标**：提供 Vsidian 自己的公开 API，供开发者编写或移植。未经修改的 Obsidian 社区插件包直接运行不作为当前目标。
- **API 分层**：提供稳定 API 与显式实验入口两层。稳定 API 纳入兼容约定和检查；实验入口供高级扩展（如 CM6 扩展）使用，须标明可能随版本调整的边界，不把内部控制器直接作为长期兼容承诺。首批稳定能力范围按下面六组确定，具体接口签名与数据模型尚待设计。
- **API 版本**：稳定 API 使用独立于 Vsidian 本体的版本号，附加组件声明支持的 API 版本范围。实验入口另行声明兼容要求，不因普通本体升级自动改变稳定 API 的兼容判断。首个版本号与实验入口具体约束尚待设计；稳定 API 的移除门槛见下文「稳定 API 弃用」。
- **发现与安装**：以 VSCode 为入口。附加组件的具体设置在 Vsidian 自有设置页汇总和控制；发现、唤醒与注册的职责顺序及首版安装侧要求已经确认，具体接口见后续接入规格。
- **识别协议**：在包清单中显式声明附加组件身份，再通过公开注册协议校验接入能力。第三方遵循公开协议即可接入，列表显示其作者、扩展 ID 和状态；市场关键词仅用于寻找。没有附加组件声明的普通扩展不进入组件列表，声明合法但 API 不兼容或加载失败的组件显示原因。声明字段名、schema 和注册载荷仍待设计，不将前轮示意字段和版本号当作已发布契约。

### 首批稳定 API 范围

2026-10-05 用户确认 Q20：首批稳定 API 覆盖以下六组能力。表中描述能力范围，不代表已有可调用的方法或已发布的接口签名。

| 分组 | 能力范围 |
| --- | --- |
| 视图与编辑 | 读取文本与选区、提交编辑、订阅输入事件 |
| 内容渲染 | 扩展代码块渲染、处理阅读模式生成的内容 |
| 操作与界面 | 新增自己的命令、菜单项、按钮或面板，接入快捷键 |
| 设置 | 注册设置、读写与订阅变化、自定义自己的设置页 |
| 生命周期与通信 | 注册与取消注册、视图创建与释放、宿主与页面通信 |
| 诊断 | 带组件来源的日志与错误上报 |

输入处理、内容渲染、界面操作三类样例共同验证首批接口；Easy Typing 移植是输入类样本。直接接入 CodeMirror 6 等底层引擎的能力继续通过实验入口开放。所有能力遵守下文的视图目标、编辑模式、界面归属、资源释放与异常恢复边界。

### 运行与作用范围

- **发现与接入顺序**（Q25，2026-10-05）：Vsidian 完成自身激活并提供可访问的 API 后，扫描附加组件身份声明，检查兼容性，再唤醒合格的 VSCode 扩展；组件代码调用公开 API 注册具体能力。Vsidian 负责发现与协调唤醒，组件代码负责能力和业务调用时机。手动停用运行功能的组件仍允许接入设置入口与定义，运行功能按用户开关启停。清单格式、注册载荷和刷新流程仍待设计。
- **首版宿主位置**（Q26，2026-10-05）：附加组件的宿主代码须与 Vsidian 在同一扩展宿主中运行。本机项目两者在本机；Remote SSH 工作区两者的宿主代码在远端。安装侧由 VSCode 管理，Vsidian 提供检查与排障提示；页面代码仍按前述约定在相应 Webview 中执行。首版采用同宿主接入路线，跨本机与远端的调用留待另行设计。
- **加载模型**（A）：包清单仅承担身份、兼容与必要展示信息。组件在 Vsidian API 就绪后由代码执行轻量接入注册；运行功能按用户开关启停，设置入口与定义可独立接入。事件订阅、能力和适用模式的注册、业务调用时机及昂贵资源的按需初始化由组件代码与生命周期 API 控制。不另建 Vsidian 平台级激活事件声明，避免与代码重复表达同一行为。
- **代码分发**：一个附加组件以一个 VSCode 扩展分发，所需的宿主代码与页面代码一同包含在它自己的 VSIX 中。宿主代码调用公开 API 接入，页面入口由组件代码注册，再由 Vsidian 装载到对应的 Webview。组件按所需能力提供代码，不要求只处理宿主功能的组件额外提供页面代码。入口载荷、模块格式与装载实现尚待设计。
- **运行位置与通信**：宿主代码处理注册、文档、文件、设置保存与网络逻辑；页面代码参与编辑器输入、内容渲染和自身设置页交互。两端通过 Vsidian SDK 提供的公开接口通信，跨边界请求与结果经消息传递。输入与光标相关回调在编辑器所在页面执行，文档写回继续遵循已有宿主文本管线。SDK 是供组件作者调用的接口与封装，具体形式尚待设计。
- **功能开关**：Vsidian 设置页提供独立的附加组件功能开关。手动关闭时停止组件在 Vsidian 中的编辑、渲染和界面操作等功能，释放这些功能的注册与资源，保留其设置入口及配置能力；具体界面行为见下文「设置界面与作用范围」。安装、卸载与整个扩展的禁用继续由 VSCode 管理。
- **默认状态**：新安装、VSCode 已启用且 API 兼容的附加组件默认启用。用户在 Vsidian 中关闭后持久保留选择，不因重启或普通升级自动开启。
- **热切换**：开关变更影响已打开文档，无需重开。输入法组合或编辑提交尚未完成时，等待输入安全落定再切换，保留原文与撤销历史。具体重配和卸载实现仍需验证。
- **视图实例**：提供主正文、悬停引用与正文嵌入共用的统一视图实例接口，组件通过代码注册适用模式。输入能力覆盖合法可编辑的 Live 实例，渲染能力作用于注册适用的视图；命令和编辑操作始终归当前目标文档，在引用 B 中编辑不误改父文档 A。
- **运行保护**：首版沿用普通 VSCode 扩展的信任模型，重点实现错误归因、注册校验、资源回收与停用恢复。不将声明校验和功能开关表述为对整个第三方扩展的安全沙箱；具体异常捕获、资源释放与重试实现尚待设计。
- **异常恢复**（2026-10-05）：当 Vsidian 能捕获并归因某个组件的注册、初始化或回调异常时，暂停该组件在 Vsidian 中的全部注册功能，释放相应注册与资源，避免留下半初始化的功能。保留用户的启用偏好，设置页显示故障原因并提供手动重试；重试失败时仍显示故障状态。暂停遵循热切换的输入安全收尾约定，不宣称终止整个 VSCode 扩展的代码。具体触发、清理与重试流程仍需设计和验证。
- **菜单边界**（2026-10-05）：附加组件可以新增属于自己的菜单项，标识使用组件命名空间，快捷键纳入统一管理和冲突检查；停用时撤下自己的新增项。内置菜单项由 Vsidian 管理，不向附加组件开放改名、隐藏、删除或替换执行逻辑的接口，也不能通过同名注册间接覆写内置项。既有内核的 `register` 覆盖行为、`override` 与隐藏入口不能原样作为公开 SDK。菜单的挂载位置、所属操作与注册载荷仍待设计。
- **调试与日志**：调试界面复用 VSCode：页面代码通过 Webview 开发者工具检查，宿主代码通过扩展调试与 Debug Console 检查。日常安装态的宿主日志写入 VSCode 输出通道，标明组件 ID、出错阶段和原因。设置页保留简短组件状态和重试入口；日志用于排障，暂停与重试由 Vsidian 生命周期机制按上述异常恢复规则执行。
- **需求覆盖**：首批稳定能力的六组范围已确认，以输入处理、内容渲染、界面操作三类样例共同验证。文件与外部服务的具体 API 和权限边界单独讨论，运行位置沿用上述宿主侧约定；具体接口签名及实现任务尚未冻结。

### 行为协调与渲染选择

**行为的管理单位**（Q27 修订，2026-10-05）：附加组件通过代码注册具体行为，即可单独管理的处理功能，例如括号补全或空格整理。用户调整某项行为的顺序或关闭该行为，组件的其他已启用行为继续按各自规则运行；整个组件的功能开关仍控制它在 Vsidian 中的运行功能。

**默认执行规则**：同一操作不一定意味着行为互斥。适用且已开启的行为默认按既定顺序依次触发，用户可以调整顺序，也可以只关闭其中部分行为。一项行为已经执行，不是平台停止后续行为的统一理由。组件通过代码判断自己的业务适用条件，平台管理注册、顺序、开关与生命周期；该决定不新增一套清单激活声明。

**行为展示信息**：注册行为时必须提供用户可读的名称；简短说明和例子推荐提供，不作为接入的强制条件。展示信息与行为代码一同注册，界面标明所属组件，以便用户判断调整对象。稳定身份、名称本地化与字段格式尚待设计。

**管理入口**：入口位于 Vsidian 的组件管理设置页，名称为「行为冲突管理」，由 Vsidian 管理。页面支持行为调序与逐项开关；用户不一定掌握组件的完整行为，不能把所有内部条件分支平铺为配置要求。分组与筛选、默认序算法、最近执行记录及其他排查展示方式仍待设计和确认。

部分行为的关闭应保留其配置，并与整个组件的停用区分。调序与开关持久化需要能稳定定位该行为；具体存储、重启恢复、热切换与资源释放实现尚待设计。行为顺序调整后的数据传递与确需独占的操作如何表达仍须明确，不能沿用前轮统一的「先接管者生效」假设。

**文本修饰与撤回**（Q29，2026-10-05）：通过公开编辑接口提交的一次文本修饰，默认作为原子操作跟踪，并具有独立的撤回边界。一个修饰操作可包含多个相关文本变更，不按每个字符或每条底层变更拆分。组件作者可明确声明某个操作非原子，表示不建立独立撤销项，不表示省略来源和变更跟踪。

非原子操作与同一目标文档的上次原子操作一起撤回，不要求作者再声明要合并到哪一次触发操作。连续的非原子修饰均归入该原子操作，但各次修饰的来源和变更仍独立跟踪。合并归属已经确认，具体编辑协议、宿主撤销与重做实现仍需验证。该规则替代此前「一次输入和全部自动处理合为一次撤销」的建议；原始输入、纯选区导航与既有内置操作仍遵循各自已有契约。

**代码块渲染的自动接管与可选调整**（Q28，2026-10-05）：所有代码块语言均可由附加组件提供替代渲染，包含已经有内置渲染的语言，例如 `mermaid`。新安装、兼容且已启用的渲染组件成功接入后，自动成为其支持语言的生效提供者，替换当前内置或其他组件的渲染。安装后直接生效，不把渲染器选择作为用户必须完成的配置步骤。

多个组件提供同一语言时，仍保留主动调整的能力，内置渲染器也作为可选项保留。自动接管结果与用户调整均须持久保存；重启、重复注册与普通升级不当作新安装而重新替换。组件通过自己的注册身份提供候选，切换生效提供者不直接改写内置实现。

渲染选择与菜单、设置页的归属约定分别适用：开放内置语言的替代渲染，不改变内置菜单项及内置设置页由 Vsidian 管理的边界。渲染器注册载荷、多候选同时接入的自动顺序、可选调整入口、视图模式适配及已挂载内容的切换实现仍待设计；安装后自动替换的产品规则已确认。

**渲染显示的接管条件**（Q30，2026-10-05）：是否接管依据实际停用状态，不把所有渲染 bug 一概当作可以自动换用内置的事件。

| 情况 | 显示规则 |
| --- | --- |
| 用户正常停用渲染器或其组件 | 交回内置显示管线 |
| 整组件故障，已被平台降级停用 | 允许内置接管，保留故障原因与组件启用偏好 |
| 组件仍在运行，渲染器逻辑出错或输出有 bug | 不自动接管，不承诺判断输出正确性或替作者修复 |

可捕获且可归因的注册、初始化或回调异常，仍按既定规则暂停组件在 Vsidian 中的全部注册功能；实际完成该停用后，属于表中的整组件降级停用情形。组件自行处理的局部失败或未被识别的错误输出，不能直接等同于整组件已经停用。

保留自动接管或用户调整所确定的渲染首选。用户重新启用或手动重试成功且首选提供者重新可用后，按原选择恢复；不自动重试故障组件。内置显示管线没有相应图形渲染能力时，沿用普通代码块显示。挂载回收、迟到结果拒收、故障提示与恢复切换仍需实现和验证。

代码块渲染仍按 Q28 选择一个生效的提供者，不因行为默认依次触发而同时运行同一语言的全部渲染器。

### 设置界面与作用范围

**统一管理**：附加组件通过 Vsidian API 注册设置定义，由 Vsidian 在自有设置页统一展示、校验与持久化，按组件 ID 隔离。组件的私有缓存与业务数据另行存储。具体设置定义与存储接口尚待设计。

**设置值类型**（Q22，2026-10-05）：附加组件用户设置支持普通值、数组与对象，例如一组替换规则。值须适配宿主与页面之间的 JSON 数据协议。该决定扩展附加组件设置的能力范围，不表示现有内置标量设置模型已经支持这些类型；具体定义格式、验证与迁移机制仍待设计。

**作用范围**（Q21，2026-10-05）：附加组件设置及其功能开关支持「用户默认 + 工作区覆盖」。每个组件设置页顶部由 Vsidian 提供「用户默认」「当前工作区」两个标签，控制本次修改写入哪一层。组件的自定义内容放在下方。

- 修改「用户默认」时，未设置覆盖的工作区跟随该默认值。
- 修改「当前工作区」时，只影响当前工作区。
- 每项提供「使用用户默认」，清除当前工作区对该项的覆盖。这个操作恢复继承关系，不是恢复组件的出厂值。

具体存储位置、无工作区时的界面与生效通知流程尚待设计。本决定针对附加组件，不变更已有内置选项的作用范围。

**设置页边界**：附加组件可以自定义自己的控件和页面布局。整体页面框架、导航、作用范围标签与组件功能开关由 Vsidian 管理；公开接口不允许接管整体设置页面、覆写内置设置页或改动其他组件的设置页。自定义内容的装配、设置读写、校验与资源释放接口尚待设计。

**停用后的设置**（Q23，2026-10-05）：关闭 Vsidian 内的功能开关后，组件仍留在侧栏，并可打开自己的设置页。普通手动停用与故障暂停采用不同的页面行为：

| 组件状态 | 功能与设置页行为 |
| --- | --- |
| 已启用且正常 | 运行已注册的功能，使用组件自己的设置页 |
| 用户手动停用 | 停止编辑、渲染和界面操作等功能，仍可使用自己的设置页修改配置 |
| 故障暂停 | 暂停组件在 Vsidian 中的全部注册功能，撤下自定义设置页代码；Vsidian 显示故障原因、日志入口与手动重试 |

故障发生前已取得设置定义时，Vsidian 可用自己的基础控件供用户修正参数，再手动重试；没有取得定义时，仅提供状态与排障入口。两种停用均保留已有设置值，故障不改写用户的启用偏好。此处的手动停用是 Vsidian 功能开关，不等同于 VSCode 整体禁用扩展。

设置定义和配置页需要具有独立于运行功能的生命周期，使已停用组件在重新打开设置页或重启后仍可配置；不能以先启用编辑或渲染功能作为配置前提。具体注册、装载与回收机制仍待设计，加载模型继续采用元数据声明与代码注册。

**侧栏结构**（2026-10-05）：三个大分组之间有视觉分隔。现有内置选项放在「选项」；官方提供的附加组件设置放在「核心组件」；第三方附加组件设置放在「第三方组件」。后两个分组均保留已启用和已停用组件的设置入口。

```text
选项
  现有内置选项
──────────────
核心组件
  已启用
  已停用
──────────────
第三方组件
  已启用
  已停用
```

**分组与故障状态**（同日确认）：组件按用户功能开关归类。用户开启但因故障暂停的组件仍放在「已启用」，标注「故障暂停」，并在平台提供的状态页保留手动重试。故障状态与启用偏好分别记录，不以移入「已停用」代替故障提示。

「核心组件」表示官方组件归属。2026-10-05 的 Q24 已确认首版采用独立 VSCode 扩展分发，共用公开 API；现有内置选项仍位于「选项」。官方归属的具体识别方式尚待设计。

### 文档与兼容维护

- **维护地位**：公开 API 文档与 CSS 样式契约同等维护，必须有项目 AGENTS 入口和相关检查。API 框架设计需同时落实文档维护与检查机制，不能仅留下文字约定。
- **文档事实源**：API 声明、兼容契约与版本对应文档保留在 Vsidian 主仓库，与实现一起审查和检查。独立示例附加组件仓库供开发者学习，Wiki 可作为展示入口；外部展示不替代主仓库的事实源。
- **稳定 API 弃用**：稳定 API 默认长期兼容。确需移除时，先发布弃用说明与替代方案；从包含该弃用的版本实际发布之日起，至少经过两个后续 API 次版本且满 30 天，才允许移除。两项门槛须同时满足，版本跨度按独立 API 版本计算，不按 Vsidian 本体版本计算。具体版本记录与自动检查尚待设计。
- **文档分发**：API 文档不要求随 Vsidian 的 VSIX 分发。独立示例仓库的名称、创建和发布，以及 Wiki 是否展示仍待后续安排，未授权当前创建或发布外部仓库。

## 影响与取舍

附加组件的发现安装机制需要与 VSCode 的扩展生命周期和本地／Remote SSH 宿主位置对齐。Vsidian 只控制附加组件在自身内注册的功能，不将功能开关状态与整个扩展的安装或禁用状态混为一谈。

官方组件与第三方组件共用分发和公开 API 路线，因此发现、兼容检查和接入流程需同时适用于两者。官方组件的需求也通过公开接口表达，可用于验证这些接口的可用性；侧栏的来源分组由 Vsidian 管理，具体识别方式仍待设计。

Vsidian 的主动唤醒发生在自身激活完成、API 可访问之后；不能在自己的激活流程中等待依赖它的组件完成激活。VSCode 也可能按原生机制自行唤醒组件，因此注册入口仍需检查身份与兼容性，并避免同一组件重复接入。上述装配约束源于已核对的依赖等待语义，具体实现仍须通过真宿主验证。

同宿主要求使首版可以采用公开导出 API 接入。VSCode 1.82.3 的稳定发现接口不能完整列出另一宿主的扩展，查询无结果不能直接归因为未安装或装错侧；设置页需区分已证实状态与尚不能确认的原因，并提供 VSCode 扩展管理与运行位置的排障入口。

加载选择 A 的原因是让代码成为能力与调用时机的单一事实源，减少清单和实现的双重维护。轻量注册与重资源初始化需分开；代码注册模型本身不保证初始化便宜，仍需落实资源生命周期、费用观测和错误恢复。原生 VSCode 扩展的激活机制不被该选择替换。

公开 API 与配套文档需要共同维护兼容性。稳定 API 的弃用期限已经确定；检查的具体范围、历史基线、文档与版本对应方式及发布门禁仍待设计，不直接复制 CSS 检查器的实现，也不宣称已有自动保障。

已有 TextDocument 权威文本、保存与撤销归属、LF 坐标、输入法及视口实例释放约定继续适用。新增附加组件机制时需要证明这些既有约定得到保留。

设置定义与自定义页面共同接入 Vsidian 的设置界面，侧栏按内置选项、官方组件与第三方组件分组。普通停用保留配置能力，故障暂停则撤下组件的自定义页面代码，要求设置入口、配置定义与运行功能分别管理生命周期。设置页和菜单均按自身归属接入，内置设置页及内置菜单项由 Vsidian 管理。

菜单新增权限不能通过底层同名注册变成覆写权限。公开注册接口需要校验命名空间、归属及内置标识冲突，不能仅隐去名为 `override` 的方法就认为符合边界。既有内核机制作为内部实现保留，本决策尚未落实为代码门控或契约测试。

代码块渲染允许同一语言拥有多个候选，其中包括内置提供者。新安装的兼容且已启用渲染组件自动接管，用户仅在需要时调整。既有图形代码块注册表及两表同步机制仍是内核实现事实；附加组件提供者的注册与选择不能直接套用单一语言对应单个渲染器的假设，需要配套接入设计和验证。

同一安装包中提供两处运行代码，让组件分别接入 VSCode 能力与编辑器页面。消息通信、页面资源许可、共享编辑器运行时与卸载需要统一装配；本决定不表明这些加载路径已经实现或通过真宿主验证。VSCode 调试工具可承载排障界面，组件来源与状态仍需由 Vsidian 的接入机制记录。

## 待决事项

接口与实现验证的草案见 [附加组件规格](../specs/vsidian-addons.md)。该文件区分已确认要求与参考接口，Q28–Q30 以本轮补充和修订后的规则为准，不将草案视为已发布 API 或门禁。

2026-10-05 已补充[接口与装载技术提议](../design/vsidian-addon-api.md)：轻量注册与运行功能分别管理，页面采用独立 IIFE 和 SDK 注入，撤销采用来源分组协调与宿主历史。隔离最小宿主的基本路线已通过，生产接入、完整历史边界、Remote SSH 及兼容门禁仍待实施和验证；这条记录不冻结提议的字段或接口名称。

同日已按用户授权建立[验证与实施批次](../specs/batch-2026-10-vsidian-addons.md)：#347 总览、#348/#349 验证、#350–#367 实施。全部开票，以依赖控制执行；#348/#349/#350 初始可认领。验证通过再放行受影响实现，票关闭不代表结论通过，当前尚未实施或发布 SDK。

- **接入**：元数据与代码注册的具体接口、页面入口与模块格式、SDK 消息协议和装载实现、发现列表的刷新、重复注册处理，以及本机与 Remote SSH 的安装侧检查和排障。Vsidian 先提供 API、再发现并协调唤醒、由组件代码注册的顺序及首版同宿主要求已经确认。
- **运行**：热切换与资源释放实现、异常触发与手动重试流程、资源费用、菜单的挂载与归属检查，以及编辑操作的具体接入。行为已确认默认依次触发、用户可调序及逐项关闭；默认序算法、数据传递与独占操作表达仍待设计。文本修饰已确认默认原子跟踪，作者声明非原子时随同一目标文档的上次原子操作撤回；编辑协议与宿主撤销、重做实现仍待验证。代码块渲染已确认新安装的组件自动替换所支持语言的显示，选择仅用于用户主动调整；正常停用及整组件故障停用后允许内置接管，仍运行的渲染 bug 不自动接管。注册、模式适配、回收与切换实现仍待设计。整体设置页面的接管、内置设置页与内置菜单项的覆写已明确不开放。
- **设置实现**：设置定义、自定义页面的装载及释放、复杂值的校验与迁移、用户默认与工作区覆盖的存储和通知、无工作区时的界面，以及官方组件归属的识别方式。作用范围、普通停用与故障后的配置行为、三个侧栏大分组及按用户开关归类的规则已经确认。
- **行为管理实现**：组件管理设置页中的「行为冲突管理」分组与筛选、调序控件、执行来源或过程展示，以及稳定行为身份、名称本地化、顺序和开关的存储与恢复。入口位置、名称必填及说明和例子推荐提供已经确认，最近输入排查等前轮 UI 提议仍待定稿。
- **API 治理**：六组稳定能力的具体接口签名、数据模型与实验入口清单、兼容判定与弃用期限的检查实现、独立示例仓库与展示发布、相关检查和发布验证。
