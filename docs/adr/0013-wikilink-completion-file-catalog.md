# 全类型文件登记与双链输入联想

## 状态

2026-10-05 用户已确认本记录中的原则，并授权在独立工作树记录共识和决策。双链输入联想与本次索引扩展尚未实施；具体交互和待决项见[专项访谈记录](../specs/wikilink-completion.md)。

## 背景

现有引用索引登记 Markdown，以及从文档引用中发现的附件目标。因此，尚未被引用的图片、PDF 或其他文件可能不在文件表中，不能仅依靠现有表生成完整的文件候选。

用户要求能够搜索各种文件，同时多数文件只需记名以加速搜索。若把全类型文件登记等同于解析全部文件内容，会扩大扫描和存储费用；若只保留已有引用目标，又会漏掉可供首次引用的文件。

## 决定

- **扩大文件登记范围**：索引的文件清单覆盖所有未被排除的文件类型，沿用现有工作区索引排除规则，包括默认的 `.git`、`node_modules` 排除。
- **登记与内容解析分别建模**：多数文件只登记名称、路径等搜索所需信息，不扫描其全文。标题与块联想仅用于 Markdown；需要内容时，以当前文档内容为依据。
- **空查询与有查询分别选候选**：空查询只列 Markdown、图片、PDF、音视频和可读文本等常用资源，按 mtime 从新到旧；有查询时允许其他类型进入匹配结果，匹配程度优先，同等匹配按 mtime 从新到旧。
- **保持目标解析语义**：文件搜索帮助用户选择明确目标，选择后生成直接来源文档相对路径。继续遵守 [ADR-0008](0008-workspace-reference-index.md) 的根内边界，不恢复按短文件名自动解析目标或跨根补查。

## 影响与技术待决

文件清单新增的规模主要由文件数决定，不要求读取全部附件内容。空查询排序所需的 mtime 必须来自文件信息，不能用候选加入缓存的时间替代。

文件清单与引用关系都仍是可重建的派生数据，不成为权威文档或资源访问许可。增删改名、排除变化、根变化与异步迟到结果需要纳入生命周期；未完成扫描不能被展示为完整结果。

本记录确定逻辑边界，不决定物理分表、持久化格式、扫描调度或查询数据结构。具体设计须协调现有索引，不能把登记所有文件推导为解析所有内容；附加组件 API／SDK 不作为本专项的前置条件。
