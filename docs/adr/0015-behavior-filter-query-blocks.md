# 输入行为管理筛选采用积木式查询构造器

## 状态

## 背景与决定

「输入行为管理」列表（数十到一两百条行为）需要筛选检索：按显示名、所属组件、ID 与启用状态过滤，并支持逻辑组合。两条路线：

- **文本搜索**：一个输入框 + 匹配口径，实现简单，但字段/状态/逻辑组合在纯文本下无法表达（除非引入查询语法，把学习成本转嫁给用户）。
- **积木式查询构造器**：搜索区不直接输文本，以三类积木可视化组合表达查询——字段积木（圆角矩形内嵌文本输入：行为/组件的显示名或 ID）、逻辑积木（菱形带缺口：AND/OR 双缺口、NOT 单缺口，可嵌任意积木）、状态积木（矩形下拉：启用状态四态）。构建支持拖拽与键盘双通道（Enter 拾取 → 方向键选缺口 → Enter 放下），选中积木及其嵌套整体发光明示删除范围。

用户选择积木式，并主导了形态设计（加号下拉三族、垃圾桶三用法、嵌套拖出抢救、顶层任意落点拖放）。

## Vsidian 的适配边界

- **求值与持久解耦**：查询树序列化与求值是 shared 层纯函数，UI 层只做编辑；求值只过滤不排序，命中保持展示全序（用户序在前、未调序项字典序、已关闭项原位）。
- **持久**：结构化查询树 + 页码按用户级跨重启持久（宿主 globalState，与行为状态存储同层），不是可丢的易失输入。
- **形态契约**：积木三形态、翻页控件、发光选中态均为新 UI 形态，实施前按 ui-patterns 技能「新形态先登记后实现」。
- **不提供文本搜索模式**：本决定弃文本直输，不并轨保留；若未来要加文本模式属新决策，不是本决定的默认延伸。

## 后果与验证

- UI 形态与持久化格式深度绑定：查询树序列化一旦落库并跨版本恢复，改动需考虑兼容——这是难逆转的核心。
- 代价：实施成本显著高于文本搜索（新形态登记、拖拽与键盘两套交互、浏览器原生键盘驱动测试）；收益：组合表达力与操作可发现性。
- 验证：求值语义走契约测试（纯函数矩阵），交互走浏览器测试（涉及 webview 输入行为合并前必跑）；规格「明确不包含」节钉住的边界（拖拽排序、预设过滤器）不因实施顺手扩围。
