# 行为禁用采用宿主层与组件层两层独立开关

## 状态

2026-10-13 用户在 #476 规格访谈中拍板（第一轮 Q14），随规格定稿接受；实施未开始。这是 vsidian-easy-typing#50「首要决断点」（`deletedBuiltinRuleIds` 与宿主 disabled 的关系）的平台侧答案。完整决策树见[实施规格](../specs/addon-behavior-disabled-state.md)。

## 背景与决定

easy-typing 规则页回归组件自管后，同一行为的启停存在两个可能的开关位置：宿主「输入行为管理」的单项禁用（平台仲裁面）与组件规则页自己的开关（`rule-state.json` / `deletedBuiltinRuleIds`）。两条路线：

- **同一开关两面**：组件规则页直接读写宿主 disabled 集——单一事实源，用户心智简单，但要求 #476 提供写入面，且组件可写平台状态，仲裁权外泄。
- **两层独立口径**：宿主层与组件层分开存储、互不感知对方存储；#476 只经只读面暴露宿主层事实。

用户拍板两层独立。#476 的只读边界（不改宿主仲裁语义）本身已排除写入路线，本决定把该边界升格为长期语义。

## Vsidian 的适配边界

- **生效 = 两层都开启（AND）**：宿主层（组件停用或单项禁用）与组件层（组件自己的规则开关）任一层关闭，该行为即不生效。
- **灰态判定归宿主层**：组件页对「宿主层任一为真」的行为行呈灰态，tooltip 区分「已在插件行为管理中被禁用」与「组件已停用」；组件层关闭的呈现是组件自己的事。
- **宿主层暴露**：独立只读面 `sdk.behaviorState`（编辑器页与设置页均提供）——`enabledState()` 快照（组件运行态 + 本组件被禁行为局部 id 集）+ `onEnabledChange()` 订阅，落库后即时通知；不提供任何写入成员。
- **组件层自管**：组件私有存储与语义（含其内置规则与用户规则的区分）不进宿主契约。

## 后果与验证

- 跨仓语义：easy-typing#50 按此消费；一旦组件按两层实现，未来若要合并为单一开关，需跨仓数据迁移与宿主写入面设计——难逆转的核心。
- 代价：同一行为存在两个开关位置，用户需理解「组件停用 / 宿主单项禁用 / 组件规则关闭」三种不生效原因（灰态 tooltip 承担解释）；收益：平台仲裁与组件自治解耦，故障与权限域隔离，宿主 disabled 语义保持简单（完整键集合，version 1 不动）。
- 验证：只读面走 API 契约门禁全流程（addonApiCatalog 同步、参考重生成、兼容检查）；两层 AND 合并语义由宿主执行链既有事实（`resolveAddonBehaviorOrder` 剔除 disabled）与组件侧各自验证，本决定不新增宿主仲裁逻辑。
