# 引用索引存储选型与三档容量基准（#195）

> 测量日期：2026-09-28。本文是工单 #195 的解读文档：给出两个候选存储引擎
> 在 1千/1万/10万篇语料上的实测结果、性能目标与实测数据的分列对照、
> 环境受限待验清单。原始数据单一事实源为
> [vault-index-storage-bench.json](data/vault-index-storage-bench.json)
> （含全部轮次中位数、轮数与运行方法自述）；本文数字均引自该文件，
> 复跑入口见「复现」节。

## 候选与结论

**结论：选用「紧凑分片快照 + 内存关系表」（下文简称快照引擎），
淘汰 SQLite（sql.js WASM 接入形态）。** 决策、淘汰理由与运维策略
（崩溃提交/恢复、多窗口协调、资源版本结构、容量与回收阈值）落档于
[ADR-0008](../adr/0008-workspace-reference-index.md)「存储选型」节，此处不重复。

两候选的操作集由对照契约测试钉住同口径（[vaultIndexSqliteCompare.test.ts](../../test/unit/vaultIndexSqliteCompare.test.ts)：
同一 `VaultIndexModel` 在两引擎间往返等价、反链查询同结果），性能数字比较
建立在「索引同一份关系数据」之上。

## 方法学与诚实边界

- **运行形态**：纯 Node 直跑（本机 Node 版本与 CPU 见报告 `meta`），非
  VSCode 1.86 扩展宿主进程内。宿主内的绝对数字会不同（进程内并发、GC、
  扩展宿主 Node 版本），**两引擎的相对结论**（查询/恢复/阻塞形态差距）
  预期保持方向一致，宿主内与远程数字归 #202 验证。
- **冷启动恢复**：每轮新起子进程加载（JS 堆与编译缓存冷）；OS 文件缓存
  在用户态无法清空，为热缓存近似，不冒充 OS 级冷启动。
- **SQLite 形态**：sql.js 1.14.2 WASM（无 native 绑定）。这正是「可兼容
  旧宿主」的唯一接入形态，也是被测对象；其写入量以 `export()` 字节近似
  （内存库无 WAL 概念）。
- **抽取器**：基准专用正则抽取器，覆盖语料生成器的全部链接形态，与生成
  器计数逐类对账相等（报告 `genCrossCheck`）；生产级抽取（代码字面量排除、
  别名、URL 编码等完整语法）归 #196，本票不宣称抽取器生产可用。
- **轮数与中位数**：首建 3 轮、冷恢复 3 轮、单文件更新 10 轮、批量 3 轮、
  反链查询 20 目标；各项中位数与轮数随数据记录（`rounds` 字段）。
- **事件循环延迟**：`perf_hooks.monitorEventLoopDelay` 直方图，报告
  mean/p99/max 的轮间最大值；监视窗口在操作结束后延迟 80ms 收尾，捕获
  同步阻塞解除后的 spike。
- **内存**：操作期间 25ms 采样 `process.memoryUsage()` 的峰值
  （heapUsed 与 rss 均在报告；sql.js 的 WASM 堆计入 rss 不计入 heapUsed）。
- **磁盘/写入量**：快照引擎为提交计划的实际写入字节与存储目录递归大小
  （回收后）；SQLite 为 `export()` 字节与落盘文件大小。

## 实测结果（中位数）

运行环境：Node v24.15.0 / AMD Ryzen 7 9700X / win32 x64 / NVMe。快照引擎
固定 16 片（片数权衡另测）。所有数字取各测量项中位数，轮数：首建 3、
冷恢复 3（新子进程）、单文件更新 10（PRNG 固定选样）、批量 3、反链查询
20 目标（入度最高目标集）。

| 指标 | 1k 快照 | 1k SQLite | 10k 快照 | 10k SQLite | 100k 快照 | 100k SQLite |
| --- | --- | --- | --- | --- | --- | --- |
| 首建总耗时（扫描+提交） | 93 ms | 96 ms | 726 ms | 770 ms | 12.33 s | 13.94 s |
| └ 其中提交阶段 | 33 ms | 34 ms | 290 ms | 342 ms | 2.25 s | 4.00 s |
| 冷启动恢复（子进程） | 16 ms | 75 ms | 101 ms | 426 ms | 1.04 s | 3.88 s |
| 单文件更新（含落盘） | 25.5 ms | 2.3 ms | 157 ms | 14.3 ms | 2.22 s | 153 ms |
| 批量 500 文件（含落盘） | 166 ms | 111 ms | 354 ms | 160 ms | 2.86 s | 316 ms |
| 反链查询（单次） | 0.2 µs | 45.7 µs | 0.3 µs | 44.6 µs | 0.5 µs | 48.3 µs |
| └ 反链索引构建（快照内存表） | 5 ms | — | 42 ms | — | 629 ms | — |
| 事件循环最长饿死（首建期） | 13 ms | 36 ms | 249 ms | 314 ms | **3.72 s** | **8.09 s** |
| 峰值 heapUsed（首建期） | 33 MB | 18 MB | 172 MB | 172 MB | 961 MB | 746 MB |
| 磁盘占用（首建后，回收后单代） | 1.3 MB | 3.0 MB | 13.0 MB | 29.8 MB | 131.3 MB | 297.4 MB |
| 写入量·首建 | 1.3 MB | 3.0 MB | 13.0 MB | 29.8 MB | 131.3 MB | 297.6 MB |
| 写入量·单文件更新 | 0.1 MB | 3.0 MB | 0.8 MB | 29.7 MB | 8.1 MB | 297.5 MB |
| 写入量·批量 500 | 1.4 MB | 3.7 MB | 13.2 MB | 31.7 MB | 131.5 MB | 299.4 MB |

SQLite 单文件/批量更新的写量为全库 `export()` 字节（sql.js 内存库每次
持久化整库导出，是该接入形态的固有行为，native SQLite 不会如此——但
native 依赖已被宿主约束排除）。

### 分片敏感性（快照引擎片数权衡，1k 档）

单文件更新耗时 / 实际写盘字节（中位，各 5 轮）：

| 片数 | 16 | 64 | 256 |
| --- | --- | --- | --- |
| 单文件更新 | 22 ms | 28 ms | 26 ms |
| 写盘字节 | 101 KB | 27 KB | 9 KB |

片数加大后写盘字节按片粒度近似线性下降（单片更小），耗时基本持平
（序列化与 hash 总量不变，IO 次数换 IO 总量）。100k 档的 2.22 s 单文件
更新是 **16 片配置**的数字（单片约 6 250 文件、重写 8.1 MB）；按片数与
写盘量的线性关系，100k 档改 256 片（单片约 390 文件）可将单次写盘降到
约 0.5 MB 量级——此为外推，非实测，#198 增量维护落地时按目标库容实测
校准片数。

### 关键观察

1. **反链查询是形态级差距**：快照引擎查询命中内存 Map（0.2–0.5 µs），
   SQLite 每次查询跨 JS/WASM 边界执行 SQL（45–48 µs，约百倍）。反链
   面板是高频交互路径，且面板打开期间常驻查询，此差距直接决定选型。
2. **冷恢复快照稳定 4 倍优势**：快照为分片 JSON 流式加载，SQLite 需
   整库 WASM 反序列化重建 B 树（100k 档 3.88 s vs 1.04 s）。「重启后
   快速恢复」目标由快照引擎达成。
3. **事件循环饿死是 SQLite 的形态性缺陷**：100k 档首建期最长 8.09 s
   不让出事件循环（同步建库 4.0 s + 全库导出约 4 s）。在扩展宿主进程
   内这意味着约 8 秒内所有扩展逻辑（含编辑器面板消息）无响应，与
   Remote SSH「不拖慢编辑」目标直接冲突。
4. **快照引擎自身的长同步段须治理**：100k 档 3.72 s 饿死来自
   `planSnapshotCommit` 的整代同步序列化（16 片大 JSON 字符串化）。
   本票测的是单次同步提交的上限；#197 接线时须分片交错让出事件循环
   （每片之间 `setImmediate`/批间 await），把单次饿生切成百毫秒级
   切片——这是接线约束，不是重新选型的理由（SQLite 的饿死来自库引擎
   内部，无法在 JS 层切片）。
5. **更新路径 SQLite 更快但生产可补偿**：单文件/批量纯事务更新 SQLite
   快一个数量级（100k 档 153 ms vs 2.22 s/316 ms vs 2.86 s），但生产
   调度本就把落盘合并为低频批量（#194 初值约 2 s 合并一次），快照在
   该节奏下的单次成本可接受，且分片粒度可调（见上节）。
6. **磁盘与写入量快照约省 2.3 倍**：列式紧凑 JSON + 继承片不重写
   （增量提交只写受影响片）对整库导出的优势。
7. **扫描占首建大头**：100k 档扫描+抽取 10.1 s（读 163.8 MB + 正则
   抽取 140 万边），两引擎共用同一路径；首建瓶颈在 IO 与抽取而非存储
   格式，与选型无关（生产抽取归 #196，性能可能不同）。

## 环境受限待验清单（Remote SSH）

本机无可用远程环境，以下项**未实测**，不以本机数据冒充远端通过：

1. **宿主进程内绝对数字**：扩展宿主（Electron 渲染侧 Node）内的首建/
   恢复/更新耗时，受宿主 GC 与并发负载影响，需在 1.86.2 真宿主集成
   环境复测（#202 集成路径）。
2. **Remote SSH 通道下的存储 IO**：storageUri 落远端文件系统（SSH 宿主
   本地盘），索引 IO 不走网络——该架构预期需要实测确认（watcher 事件
   端到端时延、远端磁盘吞吐下的大库冷恢复）。
3. **断连恢复行为**：SSH 断连重连后的核验路径（`onDidChangeWorkspaceFolders`
   / 重连事件驱动的清单核对）属 #198/#202 范围。
4. **并发窗口真实竞争**：同工作区两窗口并发提交的 CURRENT 覆盖行为在
   单测与基准外，需 #202 用两个真实宿主窗口验证回收保守性。

## #202 复测（2026-09-29，收口票对照）

整批实施完成后（#195–#202 全部落地，含 #197/#198 对快照引擎与索引模型的演进），
以同一语料、同一脚本、同一机器复测三档全操作集。复测报告为
[vault-index-storage-bench-recheck.json](data/vault-index-storage-bench-recheck.json)
（首测原档保留不动，对照只读两份 JSON）；执行日志 `logs/bench-202-recheck.log`。
快照引擎中位数对照（复测对象为**当前 HEAD 源码**，bench 口径与首测一致——
提交走同步版 `planSnapshotCommit` 上限测量，非生产 chunked 分批路径）：

| 指标（快照引擎中位） | 1k 首测 → 复测 | 10k 首测 → 复测 | 100k 首测 → 复测 |
| --- | --- | --- | --- |
| 首建总耗时 | 93 → 117 ms | 726 → 789 ms | 12.33 s → 16.08 s |
| └ 提交阶段 | 33 → 39 ms | 290 → 211 ms | 2.25 s → 2.35 s |
| 冷启动恢复 | 16 → 19 ms | 101 → 108 ms | 1.04 s → 1.10 s |
| 单文件更新 | 25.5 → 22.2 ms | 157 → 157 ms | 2.22 s → 2.60 s |
| 批量 500 文件 | 166 → 167 ms | 354 → 373 ms | 2.86 s → 3.08 s |
| 反链查询 | 0.2 → 0.35 µs | 0.3 → 0.3 µs | 0.5 → 0.7 µs |
| 反链索引构建 | 4.6 → 6.0 ms | 42 → 54 ms | 629 → 683 ms |
| 事件循环最长饿死（同步提交上限） | 13 → 14 ms | 249 → 189 ms | 3.72 s → 2.10 s |
| 磁盘占用（首建后） | 1.326 → 1.326 MB | 13.59 → 13.59 MB | 137.6 → 137.6 MB |
| 单文件更新写入量 | 87 → 88 KB | 825 → 867 KB | 8.55 → 8.58 MB |

结论与归因：

1. **无衰减迹象，量级与方向全部一致**：冷恢复、查询、批量、磁盘、写入量
   与首测同数量级小幅波动；查询仍是内存 Map 命中（亚微秒），对 SQLite 的
   形态级差距结论不变。
2. **磁盘占用三档字节级一致**（1.326 / 13.59 / 137.6 MB）——确定性快照
   产物未变，分片格式与继承结构稳定。
3. **100k 首建 +31% 与饿死 −44% 为环境项**：复测当天本机刚完成全量
   browser/integration 回归（系统 IO 与调度负载高于首测安静环境）；SQLite
   对照引擎同向变化（首建 13.94 s 档、饿死 8.09 s → 4.21 s，约 −48%）
   印证负载差异归因——两引擎代码未变（SQLite 对照物自 #195 未动），
   数字漂移只能来自环境。
4. **生产路径不承受同步上限**：bench 测的 3.72s→2.10s 饿死是同步版
   `planSnapshotCommit` 的上限口径；生产接线（`vaultIndexSnapshot.ts` 的
   chunked 分批规划，#197 按 ADR-0008 片间让出硬约束落地）在片间让出
   事件循环，单次饿死被切成百毫秒级切片——同步上限在复测中下降属环境
   波动，不构成对生产事件的性能声明。
5. ADR-0008 预算对照结论维持：三档容量下「重启快速恢复、查询即时、
   批量合并不阻塞、磁盘与写入量有界」的预算项复测全部成立；
   **Remote SSH 与扩展宿主进程内数字仍属待验**（见
   [manual-verification.md](../specs/manual-verification.md) 的 #202 节），
   不以本地复测冒充远程通过。
